## Outcome and acceptance

Separate the shared architecture from the Treasury proof case. Preserve
user-started file moves, source values and historical evidence. Provide
normative baseline Markdown, case-owned inputs, newcomer templates and
an initial deterministic contract compiler without deploying cloud changes.

Acceptance requires two independently selected cases, not a renamed
Treasury directory. Neither compilation may change shared sources or the
other case's generated products. Unknown/contradictory inputs must fail.
Native platform acceptance remains separately recorded.

## Work sequence

1. Normalize folder ownership and preserve historical approved requirements,
   plans/checkpoints and evidence with a relocation crosswalk.
2. Publish BASE-001 through BASE-023 and machine policy version 1.0.0.
   Define extension points, review boundaries and case-local outputs.
3. Register profiles; repair Treasury source paths/imports and prove
   reviewed provenance rebaselining does not change CSVs/business contracts.
4. Extract Treasury rules/Gold configuration from shared engines.
   Keep generic mechanisms in `artefacts` and reusable utilities in `deployment`.
5. Implement explicit case contract validation and deterministic draft
   compilation. Generated code is fixed trusted adapter code, not evaluated
   source prose. Keep missing semantics blocking.
6. Add complete small inventory examples and incomplete fill-in templates.
   Generate derived review Markdown, metadata and isolated runtime products.
7. Verify case isolation, forbidden overrides, unresolved inputs, missing
   references, deterministic outputs, stale generation and Treasury parity.
8. Record local results and remaining native/production gates. No implicit
   deployment, metadata activation, role change, commit or push.

## Evidence and boundaries

The preserved [metadata refactor history](../metadata_driven_medallion/plan.md)
established reusable runtime components using Treasury, not universal business
semantics or native certification. Its requirement/task IDs remain historical.
The current BASE catalogue extracts reusable constraints and every new case
must map to them.

The initial compiler does not understand arbitrary prose, certify source
keys, invent Gold measures, deploy semantic models or infer RLS. New connector,
algorithm and physical migration capabilities need separate baseline review.

## Additive SQL connector capability in baseline 1.1.0

The shared connector catalogue now distinguishes Fabric SQL Database
(`FabricSql`/`OAuth2`) from SQL Server (`SqlServer`/managed `Basic`).
Both retain the `sql` source family, lossless typed projection, immutable
Bronze CSV landing and unchanged Silver/DQ mechanisms.

Extract the existing Fabric SQL Copy activity into its shared connector
file and compose it alongside the new SQL Server activity. Resolve adapter
selection from the pinned connection type. Carry that field consistently
through Python descriptors, SQL task paging and pipeline dispatch.
Fabric SQL requires workspace/artifact geometry; SQL Server must use its
managed connection instead of fabricated Fabric database IDs.

Validate managed SQL connection/authentication/connectivity and declared
gateway references before publication. Keep the SQL Server native Copy
capability mandatory even when object capability arrays omit it.
Verify both local payloads, compiler/binding paths, mixed prerequisites,
failure cases and existing case bundles. Do not mark native SQL/Copy,
authentication or gateway execution verified from local checks.
